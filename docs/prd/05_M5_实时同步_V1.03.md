# 1. 模块概述

M5 实时同步模块负责在线对战中的实时数据同步，采用"服务端权威 + 客户端预校验"架构。所有比分裁定由服务端执行，客户端仅做即时反馈预校验。通过 matchVersion 版本号解决冲突，通过事件驱动实现实时同步。

## 1.1 架构原则

| 原则 | 说明 |
| --- | --- |
| 服务端权威 | 所有比分裁定、状态转换由服务端执行，客户端仅做预校验（即时反馈） |
| 客户端预校验 | 客户端提交前调用M2规则引擎预校验，给出即时反馈（Bust预警/Checkout提示），最终以服务端裁定为准 |
| 事件驱动 | 所有状态变更通过事件广播，客户端监听事件更新UI |
| matchVersion | 每次状态变更版本号+1，客户端比较版本号，冲突时以服务端为准 |
| 幂等提交 | 每次提交带clientTimestamp，防止重复提交 |
| 最终一致 | 短暂网络延迟后，客户端状态最终与服务端一致 |

## 1.2 模块职责

- • WebSocket连接管理（连接/断开/重连/心跳）
- • 事件发送和接收（turn_submitted/turn_undone/turn_locked等；Cricket附cricketState快照）
- • matchVersion冲突处理
- • 在线撤回锁定机制（5秒窗口+对手操作即锁定）
- • 离线重连和状态同步
- • 房间事件（玩家加入/准备/开始/观战）
- • 在线状态同步（presence）
- • 低端硬件视频流转发（在线对战）

# 2. 通信协议

## 2.1 连接协议

| 项目 | 说明 |
| --- | --- |
| 传输层 | WebSocket (wss://) |
| 认证 | 连接时携带JWT Token（query参数或header） |
| 心跳 | 每30秒客户端发送ping，服务端10秒内回复pong，3次无响应断开重连（★App↔服务端链路；App↔硬件设备保活见硬件协议文档§3.1，为10秒） |
| 重连 | 断开后指数退避重连（1s/2s/4s/8s/16s/30s最大），最多10次 |
| 消息格式 | JSON-RPC 2.0（请求/响应）+ JSON事件（服务端推送） |
| 压缩 | permessage-deflate（可选，大流量场景） |

# 3. matchVersion 冲突处理

★落地状态（2026-09-19）：已随 T6 落地，见 §12.2。版本号只对局帧携带、不进房间快照；版本冲突专用错误码 40903，冲突即清本地草稿并以最新帧刷新。

// matchVersion 是比赛状态的乐观锁
// 每次服务端状态变更，matchVersion +1
// 客户端提交时携带当前 matchVersion，服务端检查是否匹配

客户端提交流程：
1. 客户端记录当前 matchVersion（如 v=5）
2. 客户端调用 M2 预校验（即时反馈）
3. 客户端发送提交请求：
 {
 "jsonrpc": "2.0",
 "method": "submit_turn",
 "params": {
 "matchId": "xxx",
 "darts": [...],
 "clientTimestamp": 1693900800123,
 "matchVersion": 5 // 客户端当前版本
 },
 "id": 1
 }

4. 服务端处理：
 a. 获取当前比赛状态（matchVersion=5）
 b. 比较客户端版本（5）与服务端版本（5）→ 匹配
 c. 执行裁定（M2规则引擎）
 d. 更新状态，matchVersion → 6
 e. 广播 turn_submitted 事件（携带 matchVersion=6）
 f. 响应客户端：{result: {success: true, matchVersion: 6}}

5. 客户端收到响应/事件：
 a. 比较响应中的 matchVersion（6）与本地版本（5）
 b. 不匹配 → 应用服务端状态，更新本地版本为6
 c. 匹配 → 正常更新UI

冲突场景（版本不匹配）：
- 客户端提交时 matchVersion=5，但服务端已经是 v=6（对手刚提交）
- 服务端返回错误：{error: {code: 409, message: "版本冲突，当前版本=6"}}
- 客户端处理：
 a. 重新获取最新比赛状态（sync_match）
 b. 更新本地 matchVersion=6
 c. 重新应用最新状态到UI
 d. 提示用户"状态已更新，请重新操作"

sync_match 接口（重连后/冲突后同步全量状态）：
请求：{method: "sync_match", params: {matchId, lastKnownVersion: 5}}
响应：{
 result: {
 matchState: {...}, // 全量比赛状态（含gameType/targetScore/matchMode/legsToWin；Cricket时含cricketState）
 matchVersion: 8, // 当前版本
 missedEvents: [...] // 从v5到v8之间错过的事件（可选，用于增量同步）
 }
}

# 4. 在线撤回锁定机制

★落地状态（2026-09-19）：已随 T7 落地，见 §12.2。撤回窗口 5 秒，一律由服务端裁定；客户端不本地回滚，也不在点击后假装已撤。

// 在线对战撤回采用"提交即锁定 + 对手开始操作即不可撤销"混合机制
// A提交后有5秒撤销窗口，B一旦开始操作，A的撤销窗口立即关闭

服务端状态机：

状态：TURN_OPEN（撤销窗口开启）
 进入条件：A提交回合成功
 服务端动作：
 - 启动5秒定时器
 - 记录 undoDeadline = now + 5s
 - 广播 turn_submitted（A的分数立即同步给B）
 - A的客户端显示5秒撤销按钮
 - B的客户端显示"A提交了XX分"，B可以立即开始操作

 事件处理：
 a. 收到 A 的 undo_turn 请求
 → 检查当前时间 < undoDeadline
 → 是 → 回退A的分数，matchVersion+1，广播 turn_undone
 → 否 → 返回错误"撤销窗口已关闭"
 → 状态 → TURN_LOCKED

 b. 收到 B 的 player_activated 事件
 （B点击输入框/录入第一镖/点快捷按钮/点语音按钮）
 → 立即关闭撤销窗口（不等5秒）
 → 停止5秒定时器
 → matchVersion+1
 → 广播 turn_locked（reason: "player_activated"）
 → A的客户端：撤销按钮消失，Toast"回合已锁定"
 → 状态 → TURN_LOCKED

 c. 5秒定时器超时（B在5秒内无操作）
 → 关闭撤销窗口
 → matchVersion+1
 → 广播 turn_locked（reason: "timeout"）
 → A的客户端：撤销按钮自动消失
 → 状态 → TURN_LOCKED

状态：TURN_LOCKED（撤销窗口关闭）
 进入条件：B开始操作 或 5秒超时 或 A撤销成功
 服务端动作：
 - 切换到B的回合（如果是B操作触发的锁定）
 - 或等待A重新提交（如果是A撤销触发的）
 事件处理：
 - 收到 A 的 undo_turn 请求 → 返回错误"回合已锁定"
 - 收到 B 的 submit_turn → 正常处理B的提交

客户端A的UI状态：
 TURN_OPEN → 显示5秒倒计时+撤销按钮
 TURN_LOCKED(by_player) → 撤销按钮立即消失，Toast"对手已开始投镖，回合已锁定"
 TURN_LOCKED(by_timeout) → 撤销按钮自动消失，显示"回合已确认"
 TURN_UNDONE → 显示"已撤销，分数回退"，输入区恢复可用

客户端B的UI状态：
 收到 turn_submitted → 显示"A提交了XX分"，输入区立即可用（不需要等5秒）
 B开始操作 → 自动发送 player_activated 事件（无需用户手动触发）
 收到 turn_locked → 无特殊UI变化（B本来就在操作）
 收到 turn_undone → Toast"对手已撤销，比分已回退"，输入区禁用（等A重新提交）

★v1.1 Cricket说明：Cricket对局同样遵循本撤销锁定机制；撤销时服务端使用该回合的state_before快照整体恢复cricketState（closed/counts/score），并恢复legsWon（若该回合为赢局回合）。

# 5. 离线重连与状态同步

★落地状态（2026-09-19）：已随 T2 / T5 落地，见 §12.2。断网进入重连倒计时后由服务端保留成员（标记 offline），重连沿用同一席位与比分。

// 客户端网络断开后的重连流程

断开检测：
 - WebSocket onclose / onerror 事件
 - 心跳3次无响应
 - 网络状态变化（从WiFi切到蜂窝等）

断开后动作：
 1. 更新连接状态为"断开"
 2. 如果在对局中 → 显示"网络断开，正在重连..."
 3. 启动指数退避重连定时器

重连流程（指数退避）：
 尝试1: 等待1s → 连接
 尝试2: 等待2s → 连接
 尝试3: 等待4s → 连接
 尝试4: 等待8s → 连接
 尝试5: 等待16s → 连接
 尝试6-10: 等待30s → 连接
 10次都失败 → 显示"网络连接失败，请检查网络后重试"，提供"手动重连"按钮

重连成功后：
 1. WebSocket连接建立
 2. 发送认证（JWT Token）
 3. 认证成功 → 发送 sync_match 请求（携带 lastKnownVersion）
 4. 服务端返回全量比赛状态 + 当前 matchVersion + 错过的事件
 5. 客户端应用全量状态，更新 matchVersion
 6. 如果有错过的事件 → 按顺序回放事件（更新UI）
 7. 显示"已重新连接"Toast（2秒）
 8. 恢复正常对局

重连时的特殊情况：
 a. 比赛已结束（对手弃权/比赛完成）
 → 服务端返回 match_finished 状态
 → 客户端显示比赛结果页
 → 不恢复对局UI

 b. 房间已销毁
 → 服务端返回错误"房间不存在"
 → 客户端显示"房间已解散"，返回大厅

 c. 轮到自己但已经超时（在线对战60秒弃权倒计时）
 → 服务端返回当前状态（可能已经判负）
 → 如果已判负 → 显示比赛结果
 → 如果还在倒计时 → 显示剩余时间，用户可继续操作

 d. 低端硬件视频流中断
 → 重连后重新建立RTSP连接
 → 视频区域显示"正在恢复视频..."
 → 视频流恢复后正常显示

服务端的离线处理：
 - 检测到玩家WebSocket断开 → 启动60秒弃权倒计时
 - 广播 opponent_offline 事件（给对手）
 - 60秒内重连 → 取消倒计时，广播 opponent_reconnected
 - 60秒超时 → 判定弃权，广播 match_finished（对手获胜）

# 6. 低端硬件视频流转发

// 在线对战时，低端硬件的靶盘视频流推送给对手
// 轮到哪个玩家，双方屏幕显示哪个玩家的靶盘画面

视频流架构：
 玩家A手机 ←WiFi→ 低端摄像头A（A的靶盘）
 ↓ WebSocket (二进制帧)
 服务端（转发）
 ↓ WebSocket (二进制帧)
 玩家B手机 ← 显示A的靶盘画面

视频帧协议（二进制，非JSON）：
 字节0-1: 魔数 (0xD8 0x00)
 字节2-3: 版本 (0x01)
 字节4-5: 帧类型 (0x01=视频帧, 0x02=关键帧, 0x03=控制帧)
 字节6-9: 时间戳 (uint32, ms)
 字节10-13: 帧序号 (uint32)
 字节14-17: 数据长度 (uint32)
 字节18+: H.264 NAL单元数据

服务端转发逻辑：
 1. 收到玩家A的视频帧
 2. 验证A是当前投镖者（轮到A时才转发A的视频）
 3. 转发给：
 - 玩家B（对手，显示A的靶盘）
 - 所有观战者（P2靶盘动画观战，P0不转发视频）
 4. 不转发给A自己（A自己看本地视频）

当前投镖者切换时：
 - A回合结束 → 切换到B
 - 服务端广播 player_switched（currentPlayerIndex=B）
 - A的手机：停止发送视频帧（A不再是投镖者）
 - B的手机：开始发送视频帧（B的靶盘）
 - A的手机：收到B的视频帧 → 显示B的靶盘画面
 - B的手机：显示本地靶盘画面（自己的摄像头）

视频流控制：
 - 对局开始时：当前投镖者开始发送视频
 - 回合切换时：新投镖者开始发送，上一投镖者停止发送
 - 对局结束时：双方停止发送视频
 - 观战者：P0不接收视频（仅比分），P2接收视频但降级为靶盘动画

性能优化：
 - 视频分辨率：对局中720p（平衡清晰度和带宽），可设置
 - 帧率：20fps（飞镖运动不需要30fps）
 - 码率：1-2Mbps（局域网内可更高）
 - 关键帧间隔：2秒（减少重连后的恢复时间）
 - 网络差时自动降级：720p→480p→360p，20fps→15fps→10fps

延迟目标：
 - 局域网内：<200ms（采集→编码→传输→解码→显示）
 - 互联网：<500ms（可接受范围）
 - 超过1秒：显示"视频延迟较高"提示

## 8.1 客户端事件处理主循环

class RealtimeClient {
 var matchVersion: Int = 0
 var eventHandlers: [String: [Callback]] = [:]
 var pendingRequests: [Int: Promise] = [:]
 
 func handleEvent(event: RealtimeEvent) {
 // 1. 版本检查
 if event.matchVersion > matchVersion {
 // 版本落后，需要同步
 if event.matchVersion > matchVersion + 1 {
 // 跳过了多个版本，全量同步
 syncMatch(matchId: event.matchId, lastKnownVersion: matchVersion)
 return
 }
 // 只落后1个版本，正常应用事件
 matchVersion = event.matchVersion
 } else if event.matchVersion < matchVersion {
 // 旧事件，忽略
 return
 }
 
 // 2. 分发事件
 switch event.type {
 case .turnSubmitted:
 handleTurnSubmitted(event.data)
 case .turnUndone:
 handleTurnUndone(event.data)
 case .turnLocked:
 handleTurnLocked(event.data)
 case .bustOccurred:
 handleBustOccurred(event.data)
 case .checkoutOccurred:
 handleCheckoutOccurred(event.data)
 case .legFinished:
 handleLegFinished(event.data)
 case .matchFinished:
 handleMatchFinished(event.data)
 case .playerSwitched:
 handlePlayerSwitched(event.data)
 case .opponentOffline:
 handleOpponentOffline(event.data)
 case .opponentReconnected:
 handleOpponentReconnected(event.data)
 default:
 break
 }
 
 // 3. 通知业务层（M4/M7）
 notifyHandlers(event.type, event.data)
 }
 
 func submitTurn(matchId: String, darts: [Dart]) -> Promise<SubmitResult> {
 // 1. 客户端预校验（即时反馈）
 let validation = RuleEngine.validateScore(...)
 if !validation.valid {
 return Promise(error: validation.bustReason)
 }
 
 // 2. 发送请求（携带当前matchVersion）
 let requestId = generateRequestId()
 let params = [
 "matchId": matchId,
 "darts": darts,
 "clientTimestamp": Date().timestamp,
 "matchVersion": matchVersion
 ]
 
 return send(method: "submit_turn", params: params, id: requestId)
 .then { response in
 // 3. 处理响应
 if response.error?.code == 409 {
 // 版本冲突，同步后重试
 return syncMatch(matchId: matchId).then { _ in
 return self.submitTurn(matchId: matchId, darts: darts)
 }
 }
 // 成功，更新版本
 self.matchVersion = response.result.matchVersion
 return response.result
 }
 }
 
 func handleTurnLocked(data: TurnLockedData) {
 // 撤销窗口关闭
 matchVersion = data.matchVersion
 
 if data.reason == "player_activated" {
 // 对手开始操作，立即锁定
 UI.showToast("对手已开始投镖，回合已锁定")
 } else {
 // 5秒超时
 UI.showToast("回合已确认")
 }
 
 UI.hideUndoButton()
 }
}

# 11. 端口与硬件拓扑边界

M5 手机主机监听 0.0.0.0:8080，WebSocket 路径为 /ws/v1，REST 前缀为 /api/v1。T4 高端硬件同样在 8080 提供服务，但位于设备主机，路径为 /ws；同号不同主机，不构成本机端口冲突。

- 手机作为 M5 主机时仍可向同一 WiFi 内的硬件 <device-ip>:8080 发起出站连接。
- 若手机加入硬件自建 AP 而脱离房间所需局域网，则不可同时作为 M5 房间主机；限制来自网络拓扑，不来自端口号。
- 连接失败时必须结合目标 IP 与 WS 路径区分房间主机和硬件服务。

# 12.3 对局结束后的落库口径（DB v10 → v11）

• ★拍板口径：联机对局进「历史列表」，并标注来源（房间号 / 联机标签 / 判负标识），但不计入统计 / 成就 / 排行榜。理由：联机无第三方裁判，且 T8 的弃权判负会让「拔网线」变成提高数据的手段；口径可随后续决策调整。

• 实现方式不是拆表：联机局必须出现在历史里，因此与本地局同落 match_records，红线收在唯一判据 MatchStatsFilter.countsForStats；DAO 的 WHERE source <> "LAN" 只是性能前置，Repository 与成就取数按同一判据再兜一次，第二道闸是 isFormal = false。

• 读取拆两个显式入口：observeMatches()（历史口径，含联机）与 observeStatsMatches()（战绩口径，排除联机）；「看得到」与「算得进」是两件事。

• 写入侧只装配在主机的 startAsHost，客人端构造不到 recorder ⇒ 「客人不写」由装配位置保证；同一场重复触发结束只会落一行（去重放在 recorder 内部）。

• Mapper 只落流水里看得到的事实：身份取线上身份（房主端拿不到客人档案 ID，故 winnerName 独立成列），checkoutAttempts 写 0，长局 turns 只保留最近 30 条，不补不估。

• 联机只支持 X01 的权威对局；Cricket 仍只有静态观战首帧。
