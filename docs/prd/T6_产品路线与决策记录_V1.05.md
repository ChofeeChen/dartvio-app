# 5. 决策记录

## 5.1 BL-001 约战（对战预约机制）—— 状态：暂缓

提案来源：用户 2026-09-11 提案 —— 进入大厅后将「创建房间」卡片宽度改为 50%，在同高度右侧新增「约战」卡片入口，让线上对战的双方能提前按预约的时间配对，以提高房间热度。

问题定义（三根因拆分）：「大厅热度低 / 配对成功率低」不是一个问题而是三个，预约只对症其中一个：

| 根因 | 表现 | 预约是否对症 |
| --- | --- | --- |
| A 供给不足 | 根本没人打开 App | 不对症 |
| B 时间错配 | 有人，但错峰在线 | 对症 |
| C 匹配效率低 | 同时在线，却没配上 | 不对症（需快速匹配） |

一手证据（唯一来源：用户本人，身份 = 镖友）：「多次尝试在 Granboard app 随机打开在线对战，结果发现没有人」；「不可能让手机在这个页面停留 1 个小时只是为了等有人来匹配对战，且是不确定事件，成本和风险太高」；「在线配对成功率低导致我使用在线功能的意愿降低」；「1 分钟或 2 分钟并非关键」⇒ 关键变量不是等待时长，而是不确定性。证据等级：单一样本（n = 1，但为深度用户自述）；置信度：中，缺独立用户数据。

目标指标（用户 2026-09-11 确认）：大厅留存 / 日活（提高配对成功率是手段而非目标）。理想态：任何时间进入大厅都有很多在线房间可参与或观战。

为什么暂缓：

- • 预约是放大器，不是产生器：需要已有供给才能工作，当前供给为 0；
- • 低供给下预约的期望体验比即时匹配更差：即时匹配失败 =「我现在没事干」（成本 ≈ 0）；预约失败 =「我特意腾出空档，结果没人来」（沉没成本 + 期待落空）；
- • 双边冷启动死锁：预约池小 → 命中率低 → 无人敢用 → 池更小；
- • no-show 无约束：预约是软承诺，需信誉机制；当前无账号体系，无法建立履约约束；
- • 时间必须强收敛：低 DAU 下自由选时等于没有预约；只允许少数离散档位是硬性设计前提。
前置条件（需全部满足）：

- • M5 实时同步 + M6 服务端房间（当前大厅是客户端 Mock，见 §5.3）；
- • 账号体系（M1 / M10），以支撑身份与履约；
- • 真实供给：同时在线 ≥2 的时长占比达到可配对水平。

| # | 硬约束 | 理由 |

| 1 | 房间状态须为「服务端权威 + 可广播」，不得设计成纯 P2P。 | M6 已定的 P0 观战（F6.6 / A6.9 / A6.13）本质是「1 场对局 → N 个旁观者」；在 P2P 拓扑下观战与预约都无法低成本补上。这是一次架构分叉点，现在决定成本最低 |
| 2 | 补「低供给 / 空大厅」场景的验收标准。 | 当前 A6.1–A6.18 未覆盖该场景，而它将是上线初期的常态 |

## 5.2 BL-002 官方时间锚点 —— 状态：阶段① 已实现（2026-09-11）

是什么：在固定时间（如每晚 20:00–22:00）由官方设定一个公开的「官方擂台」时段，大厅展示该时段与倒计时，到点进入「进行中」状态。

落地情况：

- • 阶段① 已交付：domain/room/OfficialArena.kt + 大厅顶部「官方擂台」卡片，由真实设备时钟驱动、零新增依赖、不依赖后端；OfficialArenaTest 覆盖全部时段边界与文案口径；
- • 阶段②（到点本地提醒）未做：需新增 WorkManager + 通知依赖 + Android 13+ POST_NOTIFICATIONS 权限；
- • 待决策：时段占位为 20:00–22:00，需用真实使用数据（活跃时段分布）确认后调整；调整方式：只改 OfficialArena.START_HOUR / END_HOUR，其余（分钟换算、WINDOW_LABEL、卡片文案、空状态文案）全部派生，测试期望值亦由常量派生；
- • ⛔ 硬限制：不支持跨零点时段（如 23:00–01:00）。这不是可以稍后补的细节，而是一个静默算错陷阱：23:00–01:00 会让 00:30 被判成「尚未开赛」并显示「还有 22 小时开始」，而此刻真实语义下正在进行中。因此该配置被 requireValidWindow 显式拒绝（测试阶段即失败）。若真实活跃时段落在跨零点，这不是「改两个常量」的调整，需要先改造 stateAt 与「今晚 / 明晚」语义——请把工作量算进去；
- • 验证方式：先观察「用户是否会因为一个有名字的时间点而回来」。若连这点都验证不了，加通知权限也救不了。
为什么它比预约更适合当前阶段：

| 对比项 | 预约（BL-001） | 官方时间锚点（BL-002） |
| --- | --- | --- |
| 需要别人配合 | 是 | 否 |
| 0 供给时能否工作 | 不能 | 能（至少是可承诺的到点提醒） |
| 作用机制 | 反应已有的同时性 | 创造同时性 |
| 实现依赖 | 实时同步 + 服务端 | 纯客户端 UI 即可 |

关键差异：预约承诺「一场对局」，时间锚点只承诺「一个时间」。低供给下前者必然违约，后者不会。

成本阶梯：

| 阶段 | 内容 | 成本 |
| --- | --- | --- |
| ① | 时段展示 + 倒计时 + 「进行中」态（纯 UI） | 零新增依赖，可立即做 |
| ② | 到点本地提醒（通知） | 需新增 WorkManager + 通知依赖 + Android 13+ POST_NOTIFICATIONS 运行时权限（用户常拒绝），非免费 |
| ③ | 真实共享房间 | 依赖 M5 / M6，阻塞 |

建议先做 ①，验证「习惯锚点」是否成立，再决定 ②。

## 5.3 BL-003 大厅空状态重构 + 清除 Mock 活跃度 —— 状态：问题 1 已实现 / 问题 2 已确认延后

决策（2026-09-11，用户）：App 仍处于开发与演示阶段，Mock 活跃度暂时保留。因此下方「问题 2」的三处伪造信号现在不动，但面向真实用户分发前必须移除或标注为演示态。「问题 1」（空状态）已随 BL-002 一并交付。

问题 1：空状态把孤独用户推进空房间。M6 §5.1 已定义空状态文案「暂无公开房间 / 成为第一个创建房间的人吧 / [创建房间]」。在低供给世界里，这句话正是用户自述的糟糕体验：用户照做 → 独自留在空等候室 → 流失一个会话。

改进原则：不要把「空」渲染成一个数字，要渲染成「一个能立刻做的动作 + 一个确定的回来时间」。（「0 人在线」令人沮丧；「今晚 20:00 官方擂台」是一个回来的理由。）

问题 2（风险）：当前代码在伪造活跃度 —— data/room/LocalRoomRepository.kt 是纯客户端 Mock，且伪造了三层活跃度信号：

| 伪造项 | 位置 | 风险 |
| --- | --- | --- |
| 6 个种子房间 | seedRooms() | 用户发现是假的 → 信任崩塌 |
| 「镖友加入」delay(2600) + 随机假玩家 | simulateCompanionJoin() | 同上 |
| 观战人数自动增长 delay(2200) 自增 | startSpectatorTicker() | 最危险：用户明确说想看到「很多房间可观战」，伪造观战数正是伪造他最想信任的那个信号 |

结论：任何面向真实用户的分发前，这三处必须移除或明确标注为演示态。
