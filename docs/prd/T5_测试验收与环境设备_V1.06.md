# 2. 设备规划（开发期）

## 2.1 一页结论

| 项 | 结论 |
| --- | --- |
| 真机总数 | 3 台（2 台必备 + 1 台强烈建议）；§2.7 给出「只有 2 台」的取舍 |
| P1 主力机 | Android 15+ / 1080p / 6GB+ / 有相机 —— 每日开发、edge-to-edge、联机主机 |
| P2 下限机 | Android 8–10、RAM ≤3GB 或 ≤5.5"、有 3 键导航、插一张流量卡 —— minSdk 邻近、M12 gate 不支持态、蜂窝网络、联机对端 |
| P3 视觉固定机位 | Android 10+ / RAM ≥4GB / 相机可锁 AE-AF / 可长期插电可上支架 —— M12 专用（兼长时联机稳定性测试机） |
| 模拟器 | 覆盖版本长尾与极值配置：API 24 / API 28+2GB / API 29 / API 35 / 大屏折叠 |
| 云真机 | 只用于 OEM ROM 长尾冒烟，不必为此买机 |
| 明确不买 | 旗舰新机、平板、折叠屏、iPhone、游戏手机 |

一句话：用「3 台错位的老中青设备 + 模拟器矩阵」替代「多买几台同代机」—— 差异最大化、数量最小化。

## 2.2 为什么是 3 台：从开发需求反推，而不是从测试经验猜

| 开发需求（模块） | 对「设备数 / 设备属性」的硬要求 | 台数贡献 |
| --- | --- | --- |
| 单机闭环（M2 规则 / M3 录入 / M4 对局 / M7 UI / M9 统计成就 / M11 练习） | 1 台即可 | 复用 P1 |
| M5 实时同步 + M6 大厅：主机 / 客人 / 观战 | 主机与客人是互斥角色，必须 ≥2 个真实端点；观战是第 3 个端点（M6 P0：1 场对局 → N 旁观者） | P1 + P2（第 3 端可用模拟器） |
| M10 社交 + M1 账号 | 好友 / 邀请 / 排行榜需要 2 个不同账号同时在线；且必须走真实公网路径（不能只测同 WiFi 局域网） | P1 + P2，且 P2 要有 SIM 流量卡 |
| M12 手机视觉计分 | gate = API ≥29 且 RAM ≥4GB 且有摄像头；机位需长期固定在镖盘旁（偏轴 15–25° / 1.0–2.0 m），且要能长期供电 | 独占 1 台（P3） |
| 兼容下限与系统长尾 | minSdk = 24 / targetSdk = 37 ⇒ 必须有「尽量旧」和「尽量新」两端 | P2 承担旧端、P1 承担新端 |
| 厂商 ROM 差异（省电、后台冻结、字体 / 显示大小） | 与「主机须保持前台」直接冲突，属真实风险 | P2 优先选非原生定制 ROM 即可覆盖 |
| M8 硬件接入（BLE / USB） | 现代手机普遍支持 BLE 与 USB-OTG，无需为此单独选机 | 无 |

★关键冲突（决定「不能只有 2 台」的原因）：P2 的价值恰恰是「RAM < 4GB」（用来验证 M12 gate 的不支持分支），而 M12 开发又要求「RAM ≥4GB 且能长期挂在镖盘旁」——同一个角色无法同时满足这两条。所以 M12 一旦启动，就需要第 3 台。

## 2.3 P1 主力机（新系统）

| 属性 | 要求 | 为什么 |
| --- | --- | --- |
| 系统 | Android 15 或更高 | targetSdk = 37 ⇒ 新系统强制 edge-to-edge，底栏 / 手势条只有这类机器能暴露问题 |
| 屏幕 | 1080p，6.1–6.7"（≈360–420dp 宽） | 主流 dp 宽，是版式与非主流形态之间的基准 |
| 内存 | 6GB+ | 保证 4 人局 + 未来端侧推理的流畅下限 |
| 相机 | 有 | M12 参数量测算 / 日常预览 |
| 网络 | WiFi 5 及以上，可开热点 | 联机主机 + 规避路由器 AP 隔离 |
| 其他 | 能开开发者选项与 USB 调试；非唯一日常机 | 系统层组合测试会改字体缩放、显示大小、导航方式 |

## 2.4 P2 下限机（旧 / 低端）

| 属性 | 要求 | 为什么 |
| --- | --- | --- |
| 系统 | Android 8–10（API 26–29）优先 | 邻近 minSdk = 24 的下限；同时覆盖 API < 29 的 gate 不支持分支 |
| 内存 | ≤3GB，或屏幕 ≤5.5" | 一机两用：既压性能下限，又满足 M12 gate「内存不足」判定 |
| 导航 | 有 3 键导航 | 与 P1 的手势导航形成天然对照（底栏遮挡 / 留白差异最大处） |
| 屏幕 | ≤720p 或 ≤5.5"（≤360dp 宽） | 4 人局每席宽 ≈78dp，是最容易裁切的区间 |
| SIM | 插一张流量卡 / 副卡 | 测试「关掉 WiFi 走蜂窝」和 WiFi ↔ 蜂窝切换（M5 / M6 / M10 都需要） |
| ROM | 优先国产定制 ROM（省电策略激进） | 覆盖「联机主机被后台冻结 / 断连」这一真实风险 |

## 2.5 P3 视觉专用机（M12 固定机位）

| 属性 | 要求 | 为什么 |
| --- | --- | --- |
| 系统 | Android 10+（API ≥29） | VisionCapability.MIN_SDK = 29 |
| 内存 | 4GB 及以上 | VisionCapability.MIN_RAM_BYTES = 4GB |
| 相机 | 后摄可用，支持手动 / 锁定曝光与对焦（Camera2 LEVEL_3 / FULL 更佳） | MVP 是「镖入靶静止后单帧检测」，自动曝光漂移会直接毁掉颜色阈值与几何残差 |
| 供电 | 可长期插电（线材不挡机位），可上支架 / 夹具 | 固定机位长期在线，电池与散热要撑得住 |
| 散热 | 长时间预览不严重降频 | 视觉推理是持续负载 |
| 其他 | 可清空、可长期专用（不必是主力机） | 会被长期固定在镖盘旁 |
| 画像建议 | 旧旗舰 / 二手次旗舰 | 相机与散热好、价格低、可长期占用，比买新机划算得多 |

## 2.6 公共要求与不需要的条件

全部设备公共要求：

- • 能开 USB 调试；
- • 屏幕无坏点 / 坏区（触控不准会被误判成版式 bug）；
- • 可清空数据；
- • 只用 adb install -r 覆盖安装，不卸载（allowBackup = true 会从备份恢复，制造「数据还在」的假象）。
不需要的条件（避免过度采购）：不需要特定 CPU 品牌 / 型号（项目无厂商 SDK、无 SoC 相关能力）；不需要 5G；不需要高刷；不需要无线充电；不需要同一品牌。

## 2.7 只有 2 台的取舍

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 推荐（3 台） | P1 + P2 + P3 各司其职 | 需要一台可长期占用的旧旗舰（二手即可） |
| 只有 2 台 → 取舍 A | 取消 P3，M12 固定机位复用 P1 | P1 满足 gate，但 M12 开发期 P1 被「钉」在镖盘旁 ⇒ 不能与联机测试并行 |
| 只有 2 台 → 取舍 B | P2 选「满足 gate 的低端机」（API 29+ / 4GB+） | 丢掉 M12 gate 不支持态的验证能力（改用模拟器 gateUnsupported 兜底，真实性下降） |
| 超过 4 台 | 只在要验「3 个以上旁观者并发」时才需要 | 否则纯冗余 |

成本视角：P2 与 P3 都建议二手（老机 / 旧旗舰价格低），P1 用现有偏新机。真正要花钱的只有「P3 那台旧旗舰」，而它同时能承担长时间联机压力测试，性价比最高。

# 3. 版本覆盖策略

## 3.1 原则

真机覆盖「物理属性」（触控、屏幕形态、导航方式、相机、ROM、局域网），模拟器覆盖「版本号与配置极值」。

## 3.2 模拟器矩阵（免费、可随时切换）

| AVD | API | 关键配置 | 用途 |
| --- | --- | --- | --- |
| minApi24 | 24 | 默认 RAM | minSdk 下限能否启动（不打算为此买真机） |
| gateUnsupported | 28 | RAM 设 2GB | M12 gate「系统版本过低」与「内存不足」两条不支持分支 |
| boundary29 | 29 | RAM 4GB | gate 边界（刚好达标） |
| newest35 | 35 / 36 | 默认 | edge-to-edge 强制、通知权限等新系统行为基线 |
| bigScreen | 35 | 平板 / 折叠展开尺寸 | 大屏与折叠布局（本期不做适配，仅确认不崩） |

★V1.05 版式压测档位（与 §15 CR-13 配套）：小屏档 = wm size 720×1280 + wm density 320（等效 360×640dp），大屏档 = 1440×3120；两档各走一次投掷 / 录入 / 结算三态，判据是最底部元素不出屏且页面不出现纵向滚动（会话报告页为长列表，允许滚动）。

## 3.3 云真机（按需，不常态）

仅在需要批量 OEM ROM 冒烟时使用（自动化跑主流程 + 截图），用于发现「某品牌 ROM 上首页 / 底栏异常」这类只在真机出现的问题。不必为覆盖品牌自购设备。

## 3.4 时间维度（项目跨年）

目标版本是 targetSdk = 37 且在持续上探，因此设备策略要能「跟年」：今年 P1（新系统）→ 明年降级为 P2（下限机）→ 后年淘汰；每年只需保证「有一台当年新系统设备」即可，不必反复买新机。

## 7.2 S1 数据库升级 v4 → v5【第一优先，且必须最先做】

为什么第一：它要求设备上存在「旧版本产生的真实数据」，一旦开始后续测试、数据被新版本写过，这个机会就没了。而且本项目的 Room 迁移没有任何自动化测试（无 androidTest / Robolectric），只靠「版本号 + 注册 + schema 导出 + 编译」验证 —— 真机是唯一手段。

做法（无旧 APK 时，自己造一个）：

- • 临时把 data/local/DartVioDatabase.kt 的 version = 5 改成 4（迁移列表保持原样，Room 不会用到 4 之后的迁移），构建，把产物另存为 dartvio-v4.apk；
- • adb install -r dartvio-v4.apk；
- • 故意造三行数据（下表三行是精心选的，缺一行就测不出对应的 bug）；
| 行 | 造法 | 期望（升级后） |
| --- | --- | --- |
| A | X01：双倍结束 = 开、双倍开局 = 关 | outMode = DOUBLE_OUT（靠列默认值）、inMode = STRAIGHT_IN（靠列默认值） |
| B | X01：双倍结束 = 关、双倍开局 = 开 | outMode = STRAIGHT_OUT（靠 UPDATE 订正）、inMode = DOUBLE_IN（靠 UPDATE 订正） |
| C | Cricket 标准局一局 | bullMode = STANDARD_25_50、maxRounds = 0；outMode / inMode = 中性档（以 MatchMapper 对非 X01 的写法为准） |

依据（MIGRATION_4_5 源码）：加列时 outMode 的 DEFAULT 是 DOUBLE_OUT，因此必须补一次 UPDATE ... WHERE doubleOut = 0；inMode 的 DEFAULT 是 STRAIGHT_IN，因此必须补 UPDATE ... WHERE doubleIn = 1。

★A 行与 B 行不可互相替代：只造 A 会漏掉「两条 UPDATE 缺失」；只造 B 会漏掉「DEFAULT 写错」。这是本迁移最容易写错、且静默算错不崩溃的地方。

- • adb shell am force-stop com.dartvio.app → 拉库留档（必须先 force-stop，否则 WAL 未合并，读到的是旧快照）：adb exec-out run-as com.dartvio.app cat databases/dartvio.db > v4.db（同时确认 databases/ 下 dartvio.db-wal / -shm 是否已被合并）；
- • 改回 version = 5，构建，adb install -r；
验 5 件事：

- • 启动不崩、无「A migration from 4 to 5 was required but not found」类异常；
- • 历史记录页里三行都在，行数不变、时间戳不变（证明是升级而不是重建）；
- • 拉出 v5.db，用本机 sqlite3 核对上表期望值逐行对上；
- • PRAGMA user_version; = 5；
- • 统计页三个 Tab 的数字与升级前逐项一致（迁移是纯增量，数字不应跳变）。

## 7.6 S5 双机局域网联机（本次新增的最高价值项）

重要口径：M5 联机链路已实现且 UI 可达 —— RoomRepositoryProvider（可观察的数据源切换点：单机 Mock ↔ 联机）、OnlineRoomSession（主机 / 客人角色与重连）、ui/lobby/OnlineScreen.kt（路由 lobby/online）、内嵌 Ktor server + WS 客户端、LanEndpoint(8080)；大厅列表页还会用 flatMapLatest 跟随换源（避免「开了联机但列表仍是 Mock」）。默认源仍是本地 Mock，但「联机是否真的能跑」从未在两台真机上验证过 —— 这正是要测的。

步骤：

- • A：大厅 → 联机对战 → 「我是主机」→ 开启主机 → 记录显示的地址（192.168.x.x:8080）；
- • B：联机对战 → 「加入房间」→ 填地址 → 加入 → SyncState 应从「连接中」→「已连接」；
- • A 进大厅建房 → B 在大厅看到该房间（验证换源生效，不是本地 Mock）→ B 用房间号加入 → 两端等候页一致；
- • 开局：A 计分 → B 是否同步；B 计分 → A 是否同步（服务端权威：以主机状态为准）；
- • 观战：第 3 端（模拟器可）进入观战页，确认能看到比分推进。
异常路径（都要试，这些才是真机才能碰到的）：

- • 主机切后台 / 锁屏 → 客户端的连接是否保持（已启用前台服务保活，测试项是「保持多久」而不是「会不会断」）；
- • 关掉 B 的 WiFi → 是否显示「重连中」而非「已断开」；
- • 输入错误地址 → 格式校验与失败文案；
- • AP 隔离：若连不上，改为一台机开热点、另一台连热点（路由器 AP 隔离会阻断手机互访，这是最可能的「环境问题」而非代码问题）。

# **16. M5 联机专项验收（★V1.06 新增）**

前置：两台 Android 真机（P1 主力 + P2 下限）装同一次构建；★对外分发请用 beta 包而不是 debug 包，beta 变体必须自带 network_security_config，否则明文 ws:// 联机必挂且界面无提示。开始前记录版本号与 protocol v1（联机页脚注两侧比对）；adb 多设备必须带 -s。

执行顺序建议：SM5-11（覆盖安装迁移）放在最前 —— 它要求设备上存在旧版本产生的真实数据，★迁移必须 adb install -r，先卸载就失去了升级路径；本项目 Room 迁移没有任何自动化测试（无 androidTest / Robolectric），真机是唯一手段。

| 编号 | 验收项 | 操作 | 通过标准 |
| --- | --- | --- | --- |
| SM5-01 | 双机建连与换源 | P1 开主机并记录地址，P2 用历史 chip 填地址后加入路上先跑 2 秒自检 | SyncState 连接中 → 已连接；P2 在大厅看到 P1 的房间（证明不是本地 Mock）；两端等候页一致 |
| SM5-02 | 主机保活（T1） | P1 开主机后锁屏 2 分钟，P2 持续计分 | P2 不出现断开重连；通知被关时 P1 仍以前台运行并标记为降级，界面有提示 |
| SM5-03 | 断网即时感知（T2） | 中途关掉 P2 的 WiFi，观察提示，再打开 | 2 秒内出现「重连中」而非终态失败；恢复后自动重连且不需要用户重开连接；★未走到 FAILED |
| SM5-04 | 连不上时的文案（T3） | 故意填错 IP / 填另一网段地址 | 四类原因可区分（不可达 / 超时 / 被拒 / 其他网段），每句带下一步；★仍保留「仍然连接」兜底 |
| SM5-05 | 诊断取证（T4） | 在连不上或状态异常时打开诊断页 | 一眼看到两端版本号与 protocol v1；日志可一键复制导出；健康状态下也能看到最近一次错误 |
| SM5-06 | 重连身份连续（T5） | 对局中途关 WiFi 再打开，重连后继续投镖 | 仍是同一席位、同一准备状态、比分连续；★不是「挤掉原来的自己」 |
| SM5-07 | 重复提交（T6） | 弱网下把同一回合的提交按钮连点两次 | 只前进一回合；第二次得到冲突答复时本地草稿被清、以最新帧刷新；被拒保留草稿可重试 |
| SM5-08 | 撤回与锁定（T7） | 5 秒窗口内撤回；对手刚一操作就撤回；窗口到点 | 撤回后两端比分同步回退；对手一动按钮立即消失；到点自动锁定；★不能连续撤两次 |
| SM5-09 | 掉线判负（T8） | 对局中 P2 断网 60 秒；中途重连一次；房主掉线满宽限期 | 到点判负且 P1 收到结算（胜者是留下的那个人）；中途重连取消倒计时；房主宽限期内回来房间还在，超时解散 |
| SM5-10 | 多局与再来一局（T9） | 打 3 局 2 胜；结算页点「再来一局」 | 两端同步换局、先手回到房主；结算页仅房主有「再来一局」；点后两端回等候页且规则配置保留 |
| SM5-11 | DB v10 → v11 覆盖安装迁移 | ★adb install -r 覆盖安装（不要先卸载），装完后打开历史与统计页 | 老历史全部还在；新列默认值为 LOCAL / 空串 / 空串 / 0；★统计分母不变；无崩溃无 Room 迁移异常 |
| SM5-12 | 落库口径（T10） | 打完一局正常结束；再打一局用 SM5-09 的方式制造判负 | 两局都进历史列表并带「联机」标签与房间号，判负行额外标「对手掉线判负」；★统计 / 成就 / 排行榜三项数字均不变 |

# **16.1 判定与取证**

• 判定优先级：★先排除环境因素（AP 隔离、DHCP 换 IP、一端走蜂窝、beta 包缺明文配置），确认后再登记缺陷。

• 取证材料固定为「双 logcat + 双机录屏 + 联机诊断页日志」；缺陷单必须写明两端版本号与 protocol v1。

• ★自动失败项：DB 迁移过程中出现 Room 迁移异常、老历史丢失、统计分母变化 —— 任一出现即停止后续测试。

• 停止判据沿用 §8：同一根因连续三次失败即停止本轮，不允许「再试一次看看」。
