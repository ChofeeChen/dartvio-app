**结论：不是几何算错、也不是后端 bug，而是浏览器连不上后端（网络层）。**
- 探针（临时起 8790 端口，直接 POST `/api/sessions/{sid}/calib`，用 `zz_probe_calib` 影子会话，跑完即删）四种输入**全部 HTTP 200**：① 原标定图 824_3 复现 p95=2.82 ② 环境照按 1920/4032 等比缩放 ③ 环境照沿用 824 原始像素（故意错配）④ 只给 4 锚点不给校验点。
- 关键机理：**标定点选是纯前端行为**，页面加载后不再需要服务端 ⇒ 后端已死时用户照样能一路点完 12 个点，直到最后「求解标定」才暴露。浏览器原文 `Failed to fetch` 只表示网络层失败（服务没起 / 端口被换 / 被代理拦），与 HTTP 4xx/5xx 完全是两回事 —— 原 `api()` 把它原样抛给用户，毫无可操作性。

**前端加固（`dartvision/web/app.js`）**
1. `api()`：fetch 抛异常 → 换成「后端未连接（服务可能已停止，或本页来自已关闭的旧端口）→ 重新运行 `python run_gui.py` 再刷新本页；已点选的点位会自动保留」；另加「返回非 JSON」分支。
2. 顶部状态灯 + `pingBackend()`：25 s 心跳，并在窗口聚焦 / 页面重新可见时补探 `/api/health` ⇒ 后端消失时状态灯先变红；表头带端口号（便于发现「旧标签页连着已关闭的旧端口」）。
3. **点选序列持久化**：localStorage `dv.seq.<sid>.<img>`，按**点名**存（不能按索引 —— 「快速/完整」模式切换会让索引错配）；换图重建序列并恢复该图已有的点，只有 `startPicking` 才清空。
4. **画幅一致性告警**：标定照尺寸 ≠ 本会镖图众数尺寸时，第 1 步下方直接红字警告「H 只对这张图有效，套到镖图上判分会整体错位」。

## DartVision：基于 844_3 重做标定（p95 2.82→2.21）+ 拍摄清单进 GUI + 文案纠错

**标定结果变化**：844_3（与镖图同画幅）→ p95 **2.21 mm**（原 824_3 环境照 2.82）；靶面占宽 77.1%、mm/px 0.1559、8mm 环宽 51.3 px、模式 `manual4+ls`（4 锚点＋8 校验点一起最小二乘）。**仍超 H1 的 <1.5 mm。**

★**残差方向分解（本次核心结论）**：`calib.json` 的每个 residual 带 `true_mm/pred_mm/err_mm/dx_mm/dy_mm/radius_mm`。分解后：
| r | n | err 均 | 径向均 | 切向均 |
|---|---|---|---|---|
| 99 | 4 | 2.05 | **−2.04** | −0.16 |
| 162 | 4 | 0.52 | **−0.52** | −0.01 |
| 170（锚点） | 4 | 1.68 | **+1.67** | +0.11 |
⇒ **切向误差 ≈ 0（角度/旋转几乎完美），误差 100% 在径向，且符号随半径翻转**（内圈偏内、外圈偏外）。
这是**径向畸变/径向比例不一致**的签名，不是"手点抖了"（随机抖动会各方向都有）。所以：换更正视的机位（15–25°）重拍才有可能进 1.5 mm；加校验点数量没用（LS 已用上）。若仍不达标，需要「单应 + 径向畸变系数」模型（= 待决策项）。

**判分置信度的真公式**（`scoring.py:label_confidence`）：`conf = min(1, 最差余量 / (3 × max(1, 标定 p95)))`。

## 现象：选 844_3 提示「图片加载失败」—— 排查结论是**后端没病，是浏览器侧/服务状态**

**逐层实测**（全部排除）：
| 层 | 结果 |
|---|---|
| 文件 | 在。`data\raw\20260913_p0_iphone\微信图片_20260913112338_844_3.jpg`，2.55 MB / 3024×4032；会话 22 张**全部 missing=0** |
| Python 直调 | `load_cached` 0.12 s、`to_jpeg_bytes` 0.09 s ⇒ 1.87 MB JPEG，无异常 |
| 单张 HTTP | `/api/image?max=160` → 200 / 8.4 KB；`?` 全尺寸 → 200 / 1.87 MB / 0.3 s |
| **22 张并发** | 缩略图 wall **0.84 s**、全尺寸 wall **2.22 s**，**non-200：none** |
| 体积对比 | 844_3 ≈ 2.55 MB，最大的是 826_3/829_3/841_3（2.69 MB）⇒ **不是"这张特别大"** |

⇒ 后端与文件都正常。最可能是：**服务已停/正在重启时点的**、**浏览器还是旧缓存页**、**大图解码被浏览器中断**。

**改动（可观测性 + 自愈 + 性能）**
1. `app.js::loadImage` 重写：`<img>` 的 onerror 只有一句"失败"，现在失败时**用 HEAD 复检**把原因说出来 ——
   连不上后端（服务停了？看顶部状态灯）/ 404 文件不在原处 / 403 路径不在允许范围 / 5xx 后端读图出错 / 后端正常但浏览器解大图被打断；
   并**自动重试 1 次**，>4 s 先提示「这张图比较大，还在加载…」。
2. 图库缩略图 `onerror` → 变灰 + `title` 提示（不再是一个无声的破图）。
3. `imgio.py`：新增 `load_thumb`（**JPEG 解码期 `draft()` 降采样**）。★**只对 GUI 图库开启**：`api_image` 里 `load_cached(..., fast=0<max<=256)`；
   `load_image` 语义**未动** —— 帧差/标定/覆盖图仍走原图质量（draft 会改噪声特征，绝不能进算法链路）。
   `_cached` 的 `lru_cache` **24 → 64**（一个会话 22 图 ×（缩略+全尺寸）= 44 个条目 > 24 ⇒ 缓存持续抖动，每次切图都要重解 12M 像素）。

**验证**：缩略图 0.174 s → **0.047 s（3.7×）**，尺寸/亮度均值与旧路径一致（120×160 / mean 91.1）；全尺寸不受影响；接口全 200；冒烟 **43/43**；`node --check` 0；`read_lints` 0 诊断。
