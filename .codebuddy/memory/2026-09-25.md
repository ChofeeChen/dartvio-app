## ★★LAN 联机死锁根因实锤 + 修复（v0.1.8 / code 8）
- **真机日志实锤**：B 端「发 hello → 4s 收 hello err -2」循环 10 次进 FAILED；A 端（房主）日志却全部正常（收 hello/身份认领 复用=true/发 rooms_snapshot/客户端断开）——**连房主自己的 UI client（走 127.0.0.1）都超时** ⇒ 与 WiFi/网段无关，回包路径断了。
- **根因**：`DartVioClient.connectLoop` 里 `readerLoop()`（唯一能把响应帧按 id 分发到 `pending` 的读循环）在 `handshake()` **之后**才启动 ⇒ 握手 hello 发出后没人读回包，`deferred.await()` 必超时（`HANDSHAKE_TIMEOUT≈4s`，err -2 = `CLIENT_TIMEOUT`）。**这是 LAN 从未在真机跑通的根因**（v0.1.5 台账即标「LAN 待排查」），此前所有联机验证都走的在线（Realtime/轮询路径无此问题）。
- **修复**：`readerLoop` 先于握手 `launch`，成功路径 `reader.join()` 挂住连接块；握手失败路径 finally `reader.cancel()`。心跳失败仍走 `terminate()` → reader 退出 → join 返回 → 重连。
- **回归测试**：`net/client/ClientHandshakeEndToEndTest`（2 例）——JVM 起真 `DartVioHostServer` + 真 `DartVioClient` 对话，锁死握手时序。为此 gradle 开 `testOptions.unitTests.isReturnDefaultValues = true`（`DartVioClient` 内用 `android.util.Log`）。★这个 bug 教训：**「两边日志都说自己没错、就是对不上」的 bug，单侧单测永远发现不了，必须两端真对话**。

## ★★蜂窝在线「始终显示连接中」修复（v0.1.10 / code 10，当日第三发）
- **两个真因**（都记下来，别再踩）：
  1. `RoomStateStream` / `RoomEventStream` 的 `HttpClient(CIO) { install(WebSockets) }` **一个超时都没有**。蜂窝/弱网下 TLS 或 101 Upgrade 被中间设备挂住时 `webSocketSession` 永不返回 ⇒ `_status` 永久 CONNECTING，不报错、不重连（重连 catch 永远等不到异常）。修复：`install(HttpTimeout){connectTimeoutMillis=10s}` + 握手 `withTimeout(HANDSHAKE_TIMEOUT_MS=10s)`。
  2. **联机入口页那一行「在线状态」此前根本没在测什么**：`OnlineRoomLink.status()` 取的是 repo.status，而 status 照搬 WS 流状态；WS 是**冷流**，不进房间就不会启动 ⇒ 页面看到的只是常量初始值 CONNECTING。修复：新增 `OnlineRoomApi.ping()`（`GET /rest/v1/dartvio_rooms?select=id&limit=1`）+ 仓库 init 起 10s 探活循环。
- `status` 改为合成（不再照搬 WS）：WS LIVE→已连接；REST 探活健康→新增 `StreamStatus.POLLING_ONLY`（UI 文案「可用 · 同步较慢」，Warning 色）；连续 3 次探活失败→RECONNECTING。**理由**：在线联机的同步实际由 3s REST 轮询保证（`POLL_INTERVAL_MS`），WS 只是降低延迟；把 WS 状态当联机状态会让用户在能玩的时候以为不能玩。
