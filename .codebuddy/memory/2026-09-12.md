  2. DEMO 落点定义从「筒前端投影」（计划 V1.0，引入视差）演进到「最尖角 + 灰度剖面收敛端」求**接触点**（`tip_detect.py:215` `_tip_from_sharp_corner`、`_gray_profile_endpoint`）——**与 M12 PoC P0.3 的视差探针设计相互印证**。
  3. **最高价值增量**：`_gray_profile_endpoint`（含 C++ 加速 `event/native/dart_native.cpp`）本身**单帧可跑**，只缺种子。M12 用 TFLite 分割出镖体 mask 作种子 → 接 DEMO 灰度剖面亚像素精修 = **学习式粗定位 + 经典 CV 精修**混合管线。

## 轮数上限开放范围：规则理解 + 用户体验评估（同日第五轮，仅分析，未改代码）

**结论：不建议「全部开放」；建议按 `ScoreSink.SELF` 收口（标准 + Tactics +[可选]随机目标），不计分 / 生死局不开放。**

**五种 Cricket 子玩法的规则实况**（从代码读出）：标准 7 区(21 marks)/SELF/高分领先/10–15 轮/互等期可收敛；不计分 7 区/**无分数轴**（双方恒 0）/关满即胜/纯竞速 7–9 轮/几乎无卡局风险；生死局 7 区/得分记给对手/**低分领先**/10–15 轮/唯一「故意不关最后一区」有战术价值；Tactics 9 档(27 marks)/SELF/显著长/类别档合格 D-T 只 +1 mark ⇒ **卡局风险高，这才是它带上限的原因**；随机目标 5 区(15 marks)/SELF/**全局最短** 5–8 轮。

**两个必须记住的语义缺陷**（现状实现 = `isRoundLimitWin` 取「最高分者胜」且只对当前玩家判定）：
1. **生死局：方向相反** —— 最高分者胜 = 颁给「被对手送分最多、局面最差」的人。定稿 §4.9.8 子问题表把这写成「若沿用 WinCompare 会出现分数最低者胜、反直觉」，**该理由不成立**（那正是与玩法一致）；真问题是**策略在超时前后翻转**、主玩法被兜底规则侵蚀。
2. **不计分：退化为座位抽奖** —— 全场分恒 0 ⇒ `分 >= 最高分` 恒真 ⇒ 轮数一到**轮到的那个席位直接获胜**（2 人局永远第 2 席、4 人局永远第 4 席）。
3. **并列无法表达**（与开放范围无关的前置缺口）：定稿 ④ 写「分相同则并列」，但 `CricketLegState.winnerIndex` 单值 + `isWinningLeg` 只回答「我是否赢」⇒ 实际是「轮到者胜」。SELF 玩法也会踩（多人局全员 0 分超时）。建议文案钉死「并列按席序靠前者胜」或补 `isDraw`。

**与定稿的关系**：§4.9.8① 定的是「通用配置项」（字段层，我的建议**不改字段**：`maxRounds` 仍通用、协议/落库不动），要改的只是**设置页曝光范围**（收窄到 `ScoreSink.SELF`，与 §4.9.9④ Overkill 的作用域判据完全同构）+ ④ 后半句的并列口径。曝光点两处：`CricketSettingsForm`（gated `cricketMode == TACTICS`）、`MatchSetupScreen`；`toConfig` 里的 `if (TACTICS) … else 0` 需放开。**等用户裁决后再动代码。**
