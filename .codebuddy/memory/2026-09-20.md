## 匿名统计方案调研（用户目标升级：从「限制 100 人」→「更多初始用户 + 后台看用户数/日活，不收隐私」）
状态：**方案已给，等用户决策**（未写代码）。

### 核实到的事实（决定选型）
- **项目里没有 Supabase**（全目录搜 `supabase` 零命中）；有 INTERNET 权限、`DartVioApp`、Ktor **client** 2.3.12 + kotlinx-serialization-json。
- ★**supabase-kt 3.0.0 起强依赖 Ktor 3**（官方 MIGRATION.md：Ktor 2 项目不兼容）。本项目刻意停在 Ktor 2.3.12（minSdk 24 + **不开 desugaring**，Ktor 3 的 java.time 会在 API 24/25 **运行期** NoClassDefFoundError）⇒ **不要引 supabase-kt**，改用现有 Ktor client **裸调 Supabase REST**，零新依赖。
- Supabase 匿名登录机制：Dashboard 需开启；匿名用户走 `authenticated` role，JWT 带 `is_anonymous` claim；**IP 限速 30 请求/小时**；官方强烈建议开 invisible CAPTCHA/Turnstile；**无自动清理**，需定期 SQL 删 `is_anonymous and created_at < now() - 30 days`。

### 我的方案主张（待确认）
1. **统计必须 best-effort，绝不做成门禁** —— 沿用上一轮反对「服务端校验」的理由：飞镖在店里/地下室，没网也要能玩，只是不上报。
2. 表设计：`usage_ping(user_id uuid, day date, app_version, variant, invite_code)`；RLS **只给 insert**（不给 select/update/delete）+ `auth.uid() = user_id`；`unique(user_id, day)` 配合 PostgREST `Prefer: resolution=ignore-duplicates` 实现「一天最多一条」，天然去重防膨胀。
3. **目标冲突洞察**：「一人一码（限制）」与「更多初始用户（增长）」方向相反 ⇒ 建议把邀请码从**门禁降级为渠道标签**（人人可装、码只标记来源），既能增长又能看「哪个渠道带来的用户最活跃」。
4. 「用户数」匿名下实为**安装数**（卸载重装=新 ID、一人多机=多人），数字当趋势看不当精确值。
5. Firebase Analytics 是行业默认答案但**收集远超随机 ID**（设备/广告 ID），与用户「不收隐私」冲突，不选（已向用户说明理由）。
