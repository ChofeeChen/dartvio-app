# PRD / 文档写作规则

## 唯一现行版

- 每个主题**只有一份现行文档**。修订时在**原文件上原地升版本号**，禁止新建平行文档（`V3_xxx.md`、`xxx_新.md`、按阶段另起一份记录，都不允许）。
- 文件名里带版本号：`{序号}_{模块}_{主题}_V{major}.{minor}.md`，例 `07_M7_对局UI_V1.03.md`。
  - 修内容升 minor（`V1.02 → V1.03`）；结构重写或口径变更升 major。
- 文件改名要同步改：文件头「版本」行、变更记录表、以及别处对它的交叉引用。
- 归档/移动/删除任何文档前**先问用户**，不要自作主张。

## 变更必须留痕

- 每次修订在文档「变更记录」表**置顶插入**一行：版本 / 日期 / 变更类型 / 变更内容 / 影响范围 / 变更原因。
- 实现落地后追加「实施记录」章节（Given/When/Then 验收 + 偏差 + 门禁结果），不要另开文件记录。

## 与 App 现状对齐

- 描述功能时必须区分「**设计目标态**」与「**已实现 as-built**」，未实现的明确标注。
- PRD 与 App 冲突时，**以 App 为准更新 PRD**，并写清偏差原因；不要反过来让代码去迁就过时文档。
- 版本号、字段名、指标口径要能从代码里对得上（引用具体文件名，如 `app/build.gradle.kts`、`domain/rules/X01Rules.kt`）。

## 格式

- 现行版一律 **Markdown**（可 diff、可被 AI 直接读写）；docx 原件只作归档，不再维护。
- 用表格表达对照与清单，用 `✅ / ⚠️ / ⛔` 标注状态，数值带单位（dp / sp / 秒 / %）。
